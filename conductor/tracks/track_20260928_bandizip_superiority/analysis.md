## 1. 요구사항

v0.8.0까지 확보한 기능을 전수 점검하고, 반디집과 비교해 **어디가 부족한지**와
**어디서 앞설 수 있는지**를 구분해 다음 개발 우선순위를 확정한다. 단순 기능 나열이
아니라 "따라갈 것 / 버릴 것 / 우리만 할 것"의 판단 근거를 남기는 것이 목적이다.

## 2. 제약 사항

- **아키텍처 원칙**: 압축 포맷을 직접 바이너리 파싱하지 않는다. `struct.unpack`,
  `ctypes`, `memoryview` 사용을 `tests/test_architecture_constraints.py`가 메타 테스트로
  금지하고 있다(SECURITY.md 6번). → 신규 포맷 지원은 **신뢰할 수 있는 외부 구현에 위임**
  하는 방식만 허용된다.
- **설치 방침**: 관리자 권한 없이 HKCU + 사용자 프로필에만 설치한다.
- **런타임**: Python 3.11+ / PySide6. 네이티브 셸 확장(COM DLL)은 현재 스택 밖이다.
- **라이선스**: RAR 쓰기는 지원하지 않는다(unrar 라이선스).
- **배포**: 코드 서명 인증서가 없다. SmartScreen 경고가 최초 실행 시 항상 뜬다.

## 3. 기존 구조 분석 (v0.8.0 확보 기능 전수)

코드 기준으로 확인한 현재 기능은 다음과 같다.

**포맷**
- 압축(쓰기): ZIP, 7Z, TAR, TAR.GZ, TAR.BZ2, TAR.XZ
- 해제(읽기): 위 전체 + RAR/RAR5 + 단일 파일 압축(.gz/.bz2/.xz)
- 어댑터: `zip_adapter`(pyzipper), `sevenzip_adapter`(py7zr), `tar_adapter`(tarfile),
  `rar_adapter`(rarfile + 시스템 unrar/bsdtar), `singlefile_adapter`

**압축 기능**
- 압축 강도 4단계(저장/빠름/보통/최대), AES-256 암호화(ZIP은 WinZip AES 호환)
- 분할 압축(ZIP/7Z, 7-Zip 방식 `.001`), 메일 첨부 용량 프리셋(네이버/다음/Gmail)
- 알아서 압축, 각각 압축하기, 옵션 창(포맷·강도·암호·분할)

**해제 기능**
- 알아서 풀기(내용 보고 폴더 생성 여부 판단), 여기에 풀기, 비밀번호 재시도 다이얼로그
- cp949 깨진 한글 파일명 자동 복원, 해제 후 탐색기에서 결과 위치 열어 보여주기

**탐색기 연동**
- 우클릭 verb 5종(압축하기.../압축하기/각각 압축하기/알아서 풀기/여기에 풀기/열기)
- 파일 연결(ProgID) + OpenWithProgids + Applications 등록, 다중 선택 병합
  (`selection_collector`)

**GUI**
- 폴더 트리, 파일 목록 테이블(정렬), 좌측 이미지 미리보기 패널, 내장 이미지 뷰어
- 아카이브 편집(파일 추가/삭제, 재작성 + 원자적 교체), 내부 파일 더블클릭 열기
- 무결성 테스트, 드래그 앤 드롭(외부 → PackNine 방향만)

**보안**
- Zip Slip 방어, 압축 폭탄/엔트리 수 DoS 방어, 심볼릭·하드링크·절대경로·NTFS ADS 거부
- MoTW(Mark of the Web) 전파

**기반**
- CLI 전 기능 노출, macOS 베타(Apple Silicon), CI 6조합 테스트 + macOS 실빌드 스모크
  + pip-audit, 테스트 326개

## 5. 선택 이유 (우선순위 판단)

반디집의 30종 포맷을 전부 따라가는 것은 아키텍처 원칙(자체 파서 금지)상 불가능하고,
따라가더라도 차별점이 되지 않는다. 따라서 **"일상 사용 빈도 × 첫인상"이 큰 항목만
선별해 따라가고, 나머지 자원은 보안·개방성 축에 투자**한다.

### 권장 로드맵

**v0.9.0 — 탐색기 체감 개선 (따라가기)**
1. Windows 11 새 컨텍스트 메뉴 대응 (4-1의 #1)
2. 드래그 아웃 (#4)
3. 해제 시 중복 파일 처리 선택 (#5)

첫인상을 좌우하는 구간이다. 특히 #1은 Windows 11에서 PackNine 메뉴가 기본 메뉴에
보이지 않아 "설치했는데 메뉴가 없다"는 인식으로 직결된다.

**v0.10.0 — 속도 (따라가기)**
4. 멀티코어 압축 (#2) + 진행률에 처리 속도 표시

반디집의 대표 셀링포인트다. zlib은 압축 중 GIL을 놓으므로, ZIP은 엔트리 단위
`ThreadPoolExecutor` 병렬화만으로 실측 이득을 얻을 수 있다. 7Z는 py7zr의 스레드
옵션 확인이 선행 과제다.

**v0.11.0 — 보안 우위 명문화 (차별화)**
5. 해제 전 위협 요약 리포트 UI (차단된 엔트리·압축비·링크 유형을 사용자에게 설명)
6. 영문 README/릴리스 노트 — 오픈소스 확산 및 "감사 가능한 압축기" 포지셔닝

**v1.0.0 — 신뢰 (기반)**
7. 코드 서명 인증서 도입

### 보류 판단

- **ALZ/EGG**: 체감은 크지만 아키텍처 원칙과 정면 충돌한다(5절 리스크 참고). 별도 조사
  트랙에서 외부 바이너리 위임 가능성을 확인한 뒤 결정한다.
- **SFX / 썸네일 핸들러 / 자동 업데이트**: 우선순위 뒤로 미룬다. SFX는 백신 오탐
  가능성이, 썸네일 핸들러는 네이티브 DLL 의존이 부담이다.

## 6. 기술적 리스크

- **[치명] Win11 컨텍스트 메뉴 ↔ 코드 서명 의존성**: Windows 11 기본 컨텍스트 메뉴는
  `IExplorerCommand` COM 핸들러를 패키지(MSIX/스파스 패키지)로 등록해야 노출된다.
  스파스 패키지는 **서명이 필수**이므로, v0.9.0의 1번 항목은 사실상 v1.0.0의 코드 서명을
  선행 조건으로 끌어온다. 또한 "관리자 권한 없이 HKCU만" 방침과의 정합성 재검토가 필요하다.
  → 착수 전 별도 analysis 트랙에서 설치 방식 대안(MSIX 전환 여부)을 먼저 결론 내야 한다.
- **[높음] ALZ/EGG ↔ 아키텍처 원칙 충돌**: 두 포맷은 독점 포맷이고 신뢰할 수 있는 파이썬
  구현이 없다. 자체 파서를 쓰면 `test_architecture_constraints.py`가 실패하며, 이는 곧
  반디집과 동일한 취약점 표면을 스스로 만드는 선택이다. 외부 `unalz` 바이너리 위임이
  유일한 정합 경로이나 유지보수 상태와 라이선스 확인이 선행되어야 한다.
- **[중간] 멀티코어 압축의 정합성**: 엔트리 단위 병렬화는 아카이브 내 엔트리 순서와
  진행률 콜백 순서를 흔든다. 기존 진행률/순서 의존 테스트의 회귀 검토가 필요하다.
- **[중간] 드래그 아웃**: 아카이브 내부 파일을 탐색기로 끌어내려면 임시 폴더 실체화가
  필요하다. 임시 파일 정리 시점과 MoTW 전파 정책을 함께 정의해야 한다.
- **[낮음] 네이티브 셸 확장 도입 시 배포 복잡도**: 32/64비트 대응, PyInstaller 번들
  구조 변경이 따라온다.

## 8. 구현 결과 (2026-09-28 추가)

우선순위 2·4·5를 구현 완료했다. 1번은 착수 불가로 보류했다(사유는 아래).

| # | 항목 | 상태 | 구현 요지 |
|---|---|---|---|
| 1 | Windows 11 새 컨텍스트 메뉴 | **보류** | 빌드 도구 부재 + 서명 필요 |
| 2 | 멀티코어 압축 | **완료(부분)** | 항목별 병렬화. 6개 기준 0.26초 → 0.07초 |
| 4 | 드래그 아웃 | **완료** | `ArchiveTableWidget.startDrag` + 임시 폴더 실체화 |
| 5 | 중복 파일 처리 | **완료** | `DuplicatePolicy` 3종, staging 방식으로 전 포맷 공통 |

### 2번이 "부분"인 이유

단일 아카이브 내부의 병렬 압축은 구현하지 않았다. `zipfile`에는 이미 압축된 블록을
밀어 넣는 공개 API가 없고, 로컬 헤더를 직접 조립하려면 `struct.pack`이 필요한데 이는
`tests/test_architecture_constraints.py`가 막는 바이너리 수동 조립에 해당한다. 보안
불변식을 깨면서 얻을 이득이 아니라고 판단해, 항목끼리 독립적인 "각각 압축하기"만
병렬화했다(zlib/lzma가 GIL을 놓으므로 스레드로 실제 코어를 나눠 쓴다).

단일 아카이브 멀티코어가 필요하면 **시스템 `7z.exe`에 위임**하는 방식이 유일한 정합
경로다(RAR을 `unrar`에 위임하는 것과 동일한 구조, `-mmt=N` 사용). 별도 결정이 필요하다.

### 5번 설계 메모

중복 처리는 어댑터가 아니라 `ExtractService`에 두었다. 어댑터(zipfile/py7zr/tarfile/
unrar)는 목적지에 직접 쓰기 때문에 포맷마다 "건너뛰기"를 구현하면 4곳에 중복되고
누락이 생긴다. 충돌이 있을 때만 staging 폴더에 먼저 풀고 정책에 따라 옮기는 방식이라,
**충돌이 없는 일반 경로에는 추가 비용이 전혀 붙지 않는다**.

부수 효과로 `extract_entries`에도 MoTW 전파를 추가했다. 드래그 아웃/외부 앱으로 열기가
이 경로를 쓰는데, 지금까지는 꺼낸 파일에 다운로드 표시가 붙지 않아 보호 기제가 끊겼다.

### 1번 보류 사유 (측정 결과)

이 개발 머신에서 확인한 결과:

- C/C++ 컴파일러 없음 (`cl.exe`/`clang`/`gcc` 모두 부재, Visual Studio 미설치)
- Rust 툴체인 없음
- Windows SDK 10.0.26100.0은 존재 (`makeappx.exe`, `signtool.exe` 사용 가능)

즉 패키징 도구는 있으나 **COM DLL을 만들 컴파일러가 없다**. 여기에 스파스 패키지는
서명이 필수라, 배포까지 가려면 코드 서명 인증서가 별도로 필요하다.

### 후속 결정 필요 항목

1. 단일 아카이브 멀티코어를 위해 `7z.exe` 위임을 도입할 것인가
2. Win11 컨텍스트 메뉴를 위해 (a) 빌드 툴체인 설치 + (b) 코드 서명 인증서 구매를
   진행할 것인가, 아니면 v1.0.0까지 보류할 것인가
